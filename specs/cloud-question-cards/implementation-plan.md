# 云端桥接实施计划

目标是让员工在飞书机器人私聊查看个人事件，并在对应权限具备时让原卡或原会话收到本人操作。部署流程以 [配置 SOP](../../docs/cloud-setup-rehearsal.md) 为准。

1. **卡片与交互映射。** 在 `src/cloud/question-card.js` 解析内部版本化卡片并生成 Lark JSON 2.0。用 `test/cloud-question-card.test.js` 先钉字面文案、顺序、原选项、仅跳转、未知格式拒绝、来源 URL 和直接作答条件。第一阶段的事件格式仅用于本地示例，Raft 上游适配单独实现。飞书回调只传投递及操作引用，原选项值从服务器持久记录读取。
2. **回执与追踪。** 在同一云端入口以 SQLite 保存原事件、投递、回写和追踪回执。验证跨用户授权、重复/并发、超时回读、重启以及群追踪失败不影响原回执。配置按服务器独立，用飞书确认消息测试目标群。链路追踪只读已确认事件，先写原生结果再派发追踪。
3. **实际平台接入。** 核 Raft 的个人卡、DM、个人 @ 三类授权事件和各自的本人写回，与飞书应用机器人和真实 OAuth/回调联调。实现设置页所需的安装、双边登录、能力提示、撤销和测试步骤。Raft 权限未获证实的场景显示待开通。依 [个人消息 spec](../personal-messages/spec.md) 增加 DM 和个人 @ 的回写、测试位置和双投递去重。
4. **独立评审及首配。** 固定提交提供旧桥接回归、模拟 harness 与实际平台边界。评审者从干净克隆走 SOP，在飞书手机和桌面核渲染。修订并复验后，由维护者引导两端管理员和员工完成第一条真实投递、回写和同号追踪。

第一阶段验证命令为 `node --test test/cloud-question-card.test.js` 和 `npm test`。平台联调结果必须包含实际的 Lark 投递回执和 Raft 原生写回回执。模拟 harness 用合成内容与身份，不需要真实凭据。
