# 问题卡协议与版本

本页定义桥接与平台需要对齐的行为。字段是项目所需的数据，Raft 的接口路径、参数和权限名称等平台确认后填入实现规格。

## Raft 原生契约

| 能力 | 所需行为 |
| --- | --- |
| 投递及状态读取 | 只返回当前安装和用户已授权接收的原卡。给出稳定服务器与卡片 ID、实际答题人、格式版本、结构化题目、原卡入口、有效期及状态。支持可靠事件投递或带游标的补读。 |
| 按本人授权作答 | 在单张原卡的范围内接受指定人、题目 ID、选项值及幂等标识。按原生权限、题型和状态校验，在 Raft 原卡保存真实作答人及答案，并产生既有回执。能重新查询权威结果来处理回包丢失。 |
| 撤销 | 用户撤权、失去成员资格或服务器卸载应用后拒绝新的投递或提交，并让桥接判断旧消息已经失效。 |

Login with Raft 提供用户和服务器身份。浏览器身份登录与长期接收原卡、按本人授权提交分属不同权限。公开 OAuth 发现文档未声明 refresh token 流程。当前公开 Agent API 可准备卡片、查看发卡人自己的卡片。公开 App 事件目录尚未列原生问题卡投递，也未确认按收件人身份回答的接口。App Bot 的收件箱是该应用自身收到的消息。

## 身份和关联

- 绑定保存 Raft 服务器、应用安装、稳定用户 ID，以及飞书租户、机器人应用、该应用下的 `open_id`。同名或相同邮件地址不足以建立绑定。允许同一人分别启用多个服务器。
- 以服务器、完整原卡 ID 和答题人为一笔投递，持久化其绑定版本、原卡格式版本、飞书消息 ID 和原选项映射。解绑、重绑或应用重装后，需要重新判断投递，旧消息继续保留其原绑定版本。
- 飞书服务器回调先按官方 SDK 或受信通道验证来源，再按租户、应用、实际点击者和飞书消息查投递记录。按钮只引用该记录里的既有操作。Raft 对最终作答人、权限、卡片状态和原选项做权威校验。

## 版本演进

把 Raft 原卡格式版本作为解析入口。映射可以增添飞书交互呈现，但必须保留原文与作答约束。发布时为每个已支持版本附脱敏输入和期望映射。在用户可能点击旧卡的有效期内，保留旧映射所需的值。同一服务可兼容多版本。

已适配版本明确标为仅跳转，且用户有权查看时，飞书提供原卡入口。未登记的类型或版本留在 Raft。对仍可作答的旧卡，用原投递记录还原原题目 ID 和选项值，由 Raft 校验当前状态。环境凭据、原始事件及真实答复按部署的数据保留要求处理，公开仓库只收脱敏夹具。

## 回执与恢复

1. Raft 投递先落持久队列，再确认事件游标。重放使用相同投递关联，并尽可能沿用飞书发卡幂等键和已存消息 ID。
2. 授权点击先记录一次待提交意图，重复回调复用同一笔记录。飞书回调按平台时限确认收到后异步提交。飞书的「提交中」表示已经受理，原卡回执显示「已回答」。
3. 提交超时先查原卡。若原卡已回答，记录真实答案和回执；若确认仍可答，以同一提交号重试。状态未知时保持确认中。网页和飞书同时作答时，以 Raft 先接受的有效答案为准。
4. Raft 已成功而飞书卡面更新失败时，只补卡面。撤回、过期或解绑时停止提交，飞书显示所知终态或原卡入口。至少一次投递下要保留进程重启前后的关联和待办，避免重复原生回执。
