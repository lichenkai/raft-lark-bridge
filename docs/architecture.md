# 架构与场景

Raft Lark Bridge 按用户要完成的事划分场景。每个场景明确身份、原消息位置和完成条件，按需复用持久化、消息关联、去重和断线恢复。

| 场景 | 入口与身份 | 完成条件 |
| --- | --- | --- |
| 本地文字桥接，已实现 | 本机 `lark-cli` 用户身份读取选定会话，Raft External Agent 转给绑定的 Agent | 目标 Agent 在原转发线程发出的第一条文本答复，以选定飞书账号引用回原消息 |
| 云端问题卡，计划 | Raft App 接具名用户的原生卡，飞书应用机器人私聊投递 | Raft 原卡记录本人答案并发出原生回执 |
| 云端普通 DM 与个人 @，计划 | Raft 个人事件定位原消息，飞书机器人发带输入框的卡 | Raft 以本人身份在原会话或任务产生正式回复 |
| 执行操作的审批 | 由 Raft 原卡入口继续原生确认和权限检查 | 由原操作及其审计结果决定 |

## 已有的本地链路

一个运行实例连一个 Raft 服务器，可为不同飞书账号、会话和目标 Agent 配多条绑定。飞书历史读取和搜索补漏以原消息 ID 去重。桥接保存 Raft 转发消息和线程，等目标 Agent 的第一条文本回复，按原飞书消息 ID 引用回信。SQLite 保存投递状态、收件箱游标和重试信息。macOS 用 LaunchAgent，systemd Linux 用同一系统用户的服务。

本地身份和数据留在持有 `lark-cli` profile 的主机。换主机时在新运行账号上完成本地授权。现有配置向导、命令和 [项目 Skill](../skills/raft-lark-bridge/SKILL.md) 为这条链路服务。

## 计划中的云端链路

一套部署的桥接服务连接 Raft App 和飞书应用机器人。Raft App 在来源服务器注册一次，其他服务器分别安装。员工在设置页确认两端账号并选择接收问题卡的服务器，飞书机器人使用应用身份私发。Raft 原卡、权限、作答和回执仍由 Raft 管理。

云端链路在同一仓库内扩展。优先复用现有队列、去重、持久化和重试思路，给问题卡自己的身份绑定、投递、确认和过期规则。本地文本与云端卡片可以并行使用，配置和凭据各自独立。遇到新的业务场景，先定义实际使用与完成条件，再从已有实现提取共用代码。个人卡、普通 DM 和个人 @ 各有启用状态。 [个人消息 spec](../specs/personal-messages/spec.md)

派单实践可复用的是稳定编号关联请求和回执。现有文字桥接的飞书原消息 ID 定位引用目标。问题卡使用服务器、原卡和收件人的关联定位，通过稳定提交号查询原生作答结果。原卡版本和飞书消息 ID 随投递保存。 [协议与版本](../specs/cloud-question-cards/protocol.md)

## 改造选择与代价

当前启动时读一份 Raft 服务凭据，绑定和待办表围绕「飞书来信 → Raft Agent 回信 → 飞书引用回复」。新路径按服务器安装和员工授权分区，同时处理卡片作答、DM 和个人 @。上线顺序和失败恢复以 [配置 SOP](cloud-setup-rehearsal.md) 为准。

| 做法 | 实现与迁移成本 | 测试与回退 |
| --- | --- | --- |
| 改造现有运行入口，让它同时承载本地和云端 | 需要重新划分启动配置、进程权限和存储。若用同一数据库和生命周期，要迁移现有绑定、游标和待回信，并处理两套凭据同时存在 | 必须用旧配置和进行中的回信验升级、重启与降级。云端配置出错也需验证本地桥接能继续使用 |
| 同仓新增云端入口，按契约复用通用代码 | 需要单独的运行配置、授权、状态表和维护入口。先保留本地状态原样；只有经验证可共用的持久队列、重试等代码再提取 | 云端可独立停止、撤销和重启。本地继续跑原回归。若公共模块改动，同样验证旧配置和待回信跨重启恢复 |

建议先做同仓独立入口。等 Raft 提供可复现的个人事件和本人回写样本，用两个服务器的场景验证数据边界，再定公共代码提取范围。共用模块以两条链路都能正确恢复为准。现阶段的成本判断来自源码结构，具体数据迁移工作量等接口和首批样本确定后再估。
